Overview & Architecture

Vittam uses Firebase Remote Config to deliver soft (optional) and hard (forced) update prompts to users without pushing a new build. The version logic runs entirely on the client — Remote Config just serves version strings and flags.

App Boot Flow

main() — Firebase.initializeApp()
↓
VittamRemoteConfig.initialize() — fetch & activate RC
↓
VittamSplashScreen (min 2 s display)
↓
updateCheckProvider — compare versions
↓
update available?
↓
VittamUpdateDialog — optional or forced
↓
_AppEntry → Login / License / MainShell
💡
Non-fatal design

If Remote Config fetch fails (no internet, cold start), the app silently proceeds — fetchAndActivate errors are caught and logged with debugPrint only. Users are never blocked by an RC outage.

File-by-File Reference

3.1  lib/core/utils/semver.dart

Parses strings like "1.2.3" or "v2.0" into a comparable SemVer object.

// Safe parse — returns null on invalid input
SemVer? v = SemVer.tryParse("1.2.3");

// Strict parse — throws FormatException on invalid input
SemVer v = SemVer.parse("v2.0"); // patch defaults to 0

// Comparison operators
v1 < v2   // older
v1 > v2   // newer
v1 >= v2  // same or newer

3.2  lib/core/update/update_state.dart

Immutable model passed from provider to UI. Use the named constructor when no update is needed.

// No update needed
return UpdateState.upToDate(currentVersion);

// Update available
return UpdateState(
  updateAvailable: true,
  forceUpdate: false,
  currentVersion: "1.0.0",
  latestVersion:  "1.1.0",
  dialogTitle:    rc.updateTitle,
  dialogMessage:  rc.updateMessage,
);

3.3  lib/core/services/remote_config_service.dart

Singleton accessed via VittamRemoteConfig.instance. Call initialize() once in main(), and refresh() on app resume.

// In main()
await VittamRemoteConfig.instance.initialize();

// In app lifecycle (optional — triggers re-fetch on foreground)
VittamRemoteConfig.instance.refresh();

// Typed getters available after initialize()
rc.latestVersion           // String
rc.minimumSupportedVersion // String
rc.forceUpdate             // bool
rc.forceUpdateBelowVersion // String
rc.updateTitle             // String
rc.updateMessage           // String
ℹ️
Fetch interval

minimumFetchInterval is Duration.zero in debug builds so you can see RC changes immediately. In release builds it is 1 hour, meaning the user's device may show old values for up to an hour after you publish RC changes.

3.4  lib/core/update/update_provider.dart

Two FutureProviders. updateCheckProvider is read once per app session via ref.listen in the splash screen.

// In any ConsumerWidget
final versionAsync = ref.watch(appVersionProvider);

// In VittamSplashScreen — fires once on completion
ref.listen(updateCheckProvider, (_, next) {
  next.when(
    data: _onUpdateData,
    error: (e, __) => _onUpdateError(e),
    loading: () {},
  );
});

3.5  lib/features/update/vittam_update_dialog.dart

Call the static helper — it is a no-op when no update is available.

await VittamUpdateDialog.showIfNeeded(context, state);
// Returns null  — no update available
// Returns false — user tapped "बाद में" (Later)
// Returns true  — user tapped "अभी अपडेट करें" (Update Now)

3.6  lib/features/splash/vittam_splash_screen.dart

Enforces a minimum 2-second display regardless of how fast the RC fetch resolves. Navigation only fires after both the timer AND the update check are complete.

⚠️
Force update blocks all navigation

When forceUpdate == true the "Later" button is hidden, PopScope(canPop: false) blocks the back gesture, and barrierDismissible: false prevents tapping outside the dialog. The user cannot reach the app until they update.

Firebase Console Setup

Navigate to Firebase Console → your project → Remote Config → Create configuration.

Parameter Key Type Initial Value Purpose
latest_version String 1.0.0 Newest version available on Play Store
minimum_supported_version String 1.0.0 Oldest version allowed to run — triggers force update below this
update_title String नया अपडेट उपलब्ध है Dialog title (Hindi)
update_message String बेहतर अनुभव के लिए कृपया ऐप को अपडेट करें। Dialog body text (Hindi)
force_update Boolean false Master force-update switch (overrides version checks)
force_update_below_version String (empty) Force update for any version strictly below this value
✅
After adding all parameters, click Publish changes

Changes are live immediately but devices may cache the old config for up to 1 hour in production.

Hardcoded Defaults (in-app fallback)

If Remote Config is unreachable, these defaults kick in (defined in remote_config_service.dart):

KeyFallback value
latest_versionempty string → no dialog shown
update_titleनया अपडेट उपलब्ध है
update_messageबेहतर अनुभव के लिए कृपया ऐप को अपडेट करें।

Android Configuration

5.1  android/app/build.gradle.kts

Two changes were made:

  1. The com.google.gms.google-services plugin was added by flutterfire configure.
  2. minSdk set to maxOf(flutter.minSdkVersion, 21) — Firebase requires API 21+.
// plugins block (added by flutterfire configure)
id("com.google.gms.google-services")

// defaultConfig
minSdk = maxOf(flutter.minSdkVersion, 21)

5.2  AndroidManifest.xml

Added https scheme to the existing <queries> block so url_launcher can open Play Store links on Android 11+:

<!-- inside <manifest>, outside <application> -->
<queries>
  <intent>
    <action android:name="android.intent.action.PROCESS_TEXT"/>
    <data android:mimeType="text/plain"/>
  </intent>
  <!-- Required for url_launcher Play Store links -->
  <intent>
    <action android:name="android.intent.action.VIEW" />
    <data android:scheme="https" />
  </intent>
</queries>

Update Logic Rules

The decision tree runs in update_provider.dart every time the app launches:

Condition Result Dialog type
latest_version is blank or unparseable No dialog Silent
current version ≥ latest_version No dialog Silent
current < latest_version Update available Optional
force_update = true Forced regardless of version Force
current < minimum_supported_version Forced Force
current < force_update_below_version Forced Force
RC fetch fails (no internet, timeout) Uses cached or default values Non-fatal
🚨
Force update is permanent until the user installs the update

Once forceUpdate == true is served, the user cannot dismiss the dialog. They must go to the Play Store and update the app. Test this carefully before publishing RC changes.

How to Trigger an Update (Day-to-Day)

Optional update prompt

  • 1
    Publish new APK/AAB to Play Store (e.g. version 1.2.0).
  • 2
    In Firebase Console → Remote Config, set latest_version to 1.2.0.
  • 3
    Click Publish changes. Users on older versions will see the optional dialog next launch.

Force update (critical fix)

  • 1
    Publish fixed version to Play Store (e.g. 1.2.1).
  • 2
    Set latest_version → 1.2.1 and minimum_supported_version → 1.2.1.
  • 3
    Alternatively set force_update → true for an immediate master override.
  • 4
    Publish changes. All users below the threshold are hard-blocked until they update.
  • 5
    Once rollout is complete, set force_update back to false and publish again.
💡
To refresh RC immediately in a debug build

minimumFetchInterval is Duration.zero in debug. Hot-restart the app after publishing RC changes and it will pick them up instantly.

First-Time Setup Checklist

Use this checklist when setting up the update system in a new environment or after cloning the repo.

#StepCommand / Action
1 Install Firebase CLI npm install -g firebase-tools
2 Log in to Firebase firebase login --no-localhost
3 Activate FlutterFire CLI dart pub global activate flutterfire_cli
4 Run flutterfire configure flutterfire configure --project=vittam-ffc4c (from frontend/)
5 Verify firebase_options.dart generated Check lib/firebase_options.dart exists
6 Verify google-services.json placed Check android/app/google-services.json exists
7 Get dependencies flutter pub get
8 Add RC parameters in Firebase Console See Section 4 table above
9 Run the app flutter run
⚠️
Never commit google-services.json or firebase_options.dart to a public repo

These files contain API keys. Add them to .gitignore if the repository is public, and distribute them to team members securely.
