01

Current architecture

Verified from code

One Node.js process does everything: it serves the REST API, the marketing site, the public receipt pages, the internal admin dashboard, and the WebSocket channel. There is no load balancer, no cache tier, no queue, and no second instance. The database is the only component that already lives on separate hardware.

Application-layer constraints already coded in

  • Stateful in one place: WebSocket connections are held in an in-process Map. Two app instances behind a naive load balancer would each only reach half the devices. Horizontal scaling needs sticky sessions or a shared pub/sub — not currently built.
  • Rate limit: 200 requests per IP per 15 minutes, with trust proxy = 1. Any new proxy/CDN in front must forward X-Forwarded-For or every user gets bucketed together.
  • DB pool: max 20 connections in production, 15 s connect timeout, 30 s query timeout.
  • Sessions: JWT access tokens (8 h — the comment in .env still says 15 min; the code says 8h) + refresh tokens (30 days, stored in the DB). No server-side session store, so a host restart does not log anyone out.

-- Size on disk, per table
SELECT t.name,
       p.rows,
       SUM(a.total_pages) * 8 / 1024 AS total_mb
FROM sys.tables t
JOIN sys.indexes i      ON t.object_id = i.object_id
JOIN sys.partitions p   ON i.object_id = p.object_id AND i.index_id = p.index_id
JOIN sys.allocation_units a ON p.partition_id = a.container_id
GROUP BY t.name, p.rows
ORDER BY total_mb DESC;

-- Total DB size + growth headroom
SELECT name, size * 8 / 1024 AS size_mb, max_size, growth
FROM sys.database_files;
Licensing question that changes the quote

Ask the vendor which SQL Server edition is being proposed. Express is free but caps at 10 GB per database, 1.4 GB buffer pool and 4 cores — workable at today's size, a hard wall later. Standard is licensed per core and is a material cost. If the DB moves onto the same VM as the app, its RAM must be budgeted separately from the app's.

Non-negotiable at the edge

WebSocket upgrade must survive the proxy. If the vendor puts a load balancer, WAF, or CDN in front, it must pass Upgrade/Connection headers on /ws and allow long-lived idle connections — the app heartbeats but idle timeouts under ~60 s cause reconnect storms. It must also forward X-Forwarded-For, or the rate limiter treats every customer as one IP and locks the whole userbase out at 200 requests.

Allowed browser origins are pinned in config, not wildcarded: https://vittam.vengurlatech.com plus localhost dev ports. Mobile clients send no Origin header and are always allowed.

Recommended target sizing

Given a single-threaded Node process, a remote database, and no in-process caching, this workload is small. Do not let a vendor upsell on core count — it buys nothing until the app is clustered.

TiervCPURAMDiskFits
Minimum viable24 GB60 GB SSDApp only, DB stays remote
Recommended48 GB100 GB SSDApp + headroom for a second process and log growth
App + SQL on one box4–816 GB200 GB SSDOnly if you also bring the database in-house

Prefer disk IOPS and single-core clock speed over core count. If the database is being moved onto the same machine, add its RAM on top of the app's — SQL Server will consume whatever it is allowed to, and must be capped explicitly with max server memory.

Peak utilization metrics

Needs a measurement

Not currently collected. The app emits structured pino logs but there is no metrics agent, no APM, and no historical CPU/RAM series. Anything quoted without measuring would be invented. Below is what to run, and what the workload's shape already tells you.

Collect for 7 days, then quote the 95th percentile

# Windows — 5-minute samples to CSV, run as a scheduled task
typeperf "\Processor(_Total)\% Processor Time" ^
         "\Memory\Available MBytes" ^
         "\Process(node)\% Processor Time" ^
         "\Process(node)\Working Set - Private" ^
         "\Web Service(_Total)\Current Connections" ^
         -si 300 -o C:\perf\vittam.csv

# SQL Server — top waits and buffer pressure
SELECT TOP 20 wait_type, wait_time_ms, waiting_tasks_count
FROM sys.dm_os_wait_stats ORDER BY wait_time_ms DESC;

Derive real peak concurrency from your own data

Bills carry timestamps, so the busiest minute the system has ever seen is already recorded. This is more honest than a CPU graph for capacity planning: 

-- Busiest minute ever, and active businesses in it
SELECT TOP 20
       DATEADD(minute, DATEDIFF(minute, 0, created_at), 0) AS minute,
       COUNT(*)                    AS bills,
       COUNT(DISTINCT business_id) AS active_businesses
FROM bills
GROUP BY DATEADD(minute, DATEDIFF(minute, 0, created_at), 0)
ORDER BY bills DESC;

Blocker / risk

Ask the vendor to quote against these
  • SQL: nightly full + hourly differential or log shipping, retained 30 days, stored off the app host. State the RPO in hours.
  • Uploads directory: included in the file backup, or on object storage with versioning.
  • VM snapshot: daily, retained 7 days — covers .env and the service account file.
  • Restore drill: one documented, actually-executed restore before cutover. An untested backup is not a backup.
Fix before handing this repo to anyone

backend/notes.txt is committed to Git and contains a live ADMIN_SECRET for the licence-activation endpoint. Rotate that secret and remove the file from the working tree. Anyone with repository access can currently activate or extend licences.

Why a self-signed or mismatched cert breaks the product

The shipped Flutter app pins its API base URL to https://vittam.vengurlatech.com/api at compile time, and Android blocks cleartext HTTP by default. A certificate error is not a warning users can click through — the app simply fails to connect, for every installed copy, until a new release ships through the Play Store. Validate the certificate from a real Android device before cutover, not just from a browser.

Database TLS — worth fixing during the move

The database connection sets encrypt: true but also trustServerCertificate: true in production, which encrypts the traffic while skipping certificate validation. Traffic is protected from passive eavesdropping but not from an active man-in-the-middle. If the new database has a properly issued certificate, set DB_SSL_CA and turn that flag off — the code already supports a custom CA file.

Cutover constraints

Blocker / risk

The binding constraint is not the server. It is that thousands of already-installed app copies have the hostname compiled into them, and they cannot be reconfigured remotely.

Hard constraints — not negotiable

ConstraintWhyConsequence of ignoring
Hostname cannot changebaseUrl is a compile-time constant in the Flutter clientEvery installed app breaks until a Play Store release reaches each device
Move by DNS, not by URLSame name must resolve to the new IPSame as above
Old host stays live through DNS propagationBoth must answer during the TTL windowSplit-brain: some shops bill against the old DB, some the new
Database is the single source of truthTwo live app hosts on two DBs = divergent billsUnreconcilable accounting data
backend/uploads/ must be copied manuallyDeliberately outside the deploy directory; CI force-pushes over public/All item photos disappear
Old receipt links must keep resolving/receipt/* URLs are already in customers' WhatsApp historyCustomers hit dead links indefinitely
JWT secrets must be carried over verbatimNew secrets invalidate every issued tokenEvery user logged out mid-shift, forced to re-OTP

Timing

  • Window: 02:00–05:00 IST. This is a live billing system for shops and restaurants; any daytime interruption means a merchant cannot take payment.
  • Avoid month-end and month-start — GST and reporting periods.
  • Drop the DNS TTL to 300 s at least 48 hours ahead, restore it after.
  • DB migrations (npm run migrate:up) run against a quiesced database. Every migration has a rollback script — confirm which one is applied last before starting.

Pre-cutover checklist

  • .env recreated on the new host with identical JWT secrets — it is gitignored and will not arrive with the code.
  • Firebase service-account JSON placed on the new host.
  • New server's outbound IP whitelisted by the SQL host, if it filters by IP. Verify this early — it is the most common cutover failure.
  • web.config temp path and Node binary path corrected for the new machine.
  • Certificate installed and validated from a physical Android device.
  • CORS_ORIGINS and RECEIPT_BASE_URL reviewed.
  • Deploy mechanism from the backend branch re-established and proven with one test deploy.
  • Backup and restore drill completed — see §7.
  • Rollback plan: keep the old host intact and bootable for 7 days. Do not decommission on day one.
Worth raising with the vendor

Nothing in the application code is Windows-specific — the dependency tree is pure JavaScript and there are no native modules. Only web.config and two hard-coded paths tie it to IIS. A Linux VM with nginx and a process manager would run this stack unchanged, at lower licence cost and with simpler TLS automation, provided the SQL Server host stays where it is. Ask for both quotes and compare.
